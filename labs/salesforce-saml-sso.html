Salesforce SAML SSO Integration with Azure AD

Enterprise Single Sign-On using SAML 2.0 Protocol

Project Overview

Configured enterprise Single Sign-On between Microsoft Azure AD (Entra ID) and Salesforce Developer Edition using SAML 2.0 protocol in a hybrid lab environment.

Technologies Used

  • Microsoft Azure AD (Entra ID)
  • Salesforce Developer Edition
  • SAML 2.0 Protocol
  • X.509 Digital Certificates (RSA-SHA256)
  • Browser DevTools Network Analysis

Environment Details

  • Identity Provider: Microsoft Azure AD (Entra ID)
  • Service Provider: Salesforce Developer Edition
  • Protocol: SAML 2.0
  • Authentication: Federated identity via SAML assertions

Implementation

Azure AD Configuration

  1. Created enterprise application for Salesforce from Azure AD gallery
  2. Configured SAML-based Single Sign-On
  3. Set Entity ID and Reply URLs for Salesforce instance
  4. Mapped user attributes as SAML claims
  5. Downloaded and deployed SAML signing certificate

Salesforce Configuration

  1. Enabled SAML in Salesforce Single Sign-On Settings
  2. Created Identity Provider configuration using Azure AD metadata
  3. Configured SAML identity matching and assertion validation
  4. Deployed My Domain for SSO authentication
  5. Created user accounts with Federation ID mapping

Identity Provider claim configuration controlling user attributes sent in SAML assertion

Required Claim

  • Unique User Identifier (Name ID): user.userprincipalname
  • Sent as SAML NameIdentifier element
  • Maps to Salesforce Federation ID field
  • Format: Email address

Additional Claims

  • emailaddress: user.mail
  • givenname: user.givenname
  • surname: user.surname
  • name: user.userprincipalname
  • username: user.userprincipalname (Salesforce requirement)

Troubleshooting Case Study

Problem

SSO authentication failed with error: "We can't log you in because of an issue with single sign-on"

Initial Analysis

  1. Verified Salesforce user was active ✓
  2. Confirmed Federation ID matched SAML NameID exactly ✓
  3. Enabled case-insensitive Federation ID matching ✓
  4. Decoded SAML response - assertion structure was valid ✓
  5. All claims were present and formatted correctly ✓

Root Cause Discovery

Reviewed Salesforce SAML configuration and identified misconfiguration:

❌ Incorrect Setting

SAML Identity Type: "Assertion contains the User ID from the User object"

Why This Failed:

  • Salesforce User ID is an 18-character alphanumeric internal identifier (e.g., 005xx000001X8Uz)
  • Azure AD sent NameID in email format: Nigel@NigelTech.onmicrosoft.com
  • Salesforce attempted to match email-formatted NameID against internal User ID field
  • Match would never succeed due to incompatible formats

✅ Corrected Setting

SAML Identity Type: "Assertion contains the Federation ID from the User object"

Why This Worked:

  • Federation ID field designed for external identity federation
  • Accepts email-formatted identifiers from external IdPs
  • Properly matches incoming SAML NameID to Salesforce user record

Result

Immediate SSO authentication success. All subsequent login attempts successful as evidenced by Azure AD sign-in logs.

Key Learning

Salesforce provides three different user identifier fields for SAML matching:

  1. User ID: Internal 18-character Salesforce record identifier (for Salesforce-to-Salesforce)
  2. Username: Login username field (can work but not recommended for federation)
  3. Federation ID: Specifically designed for external identity provider integration ✅

Understanding which field to use for identity matching is critical for successful SSO troubleshooting.

Security Features

Authentication Security

  • Certificate-based trust: X.509 digital certificate validates SAML assertions
  • Signature validation: RSA-SHA256 algorithm prevents token forgery
  • Audience restriction: SAML tokens restricted to specific Salesforce Entity ID
  • Time-bound tokens: NotBefore and NotOnOrAfter conditions prevent replay attacks
  • Secure binding: HTTP POST prevents token exposure in URLs

Audit and Compliance

  • Azure AD sign-in logs: Complete audit trail of authentication events
  • Salesforce login history: Service Provider maintains access logs
  • Federation ID matching: Ensures correct user identity mapping
  • Case-insensitive matching: Enabled for Federation ID field

SAML Protocol Flow

Step 1: Service Provider Initiated SSO

User navigates to Salesforce and clicks "Azure_AD_SSO" button

Step 2: SAML Authentication Request

Salesforce generates SAML AuthnRequest and redirects browser to Azure AD

<samlp:AuthnRequest>
  <saml:Issuer>https://orgfarm-ce698c619e-dev-ed.develop.my.salesforce.com</saml:Issuer>
  <samlp:NameIDPolicy Format="emailAddress"/>
</samlp:AuthnRequest>

Step 3: User Authentication

User authenticates with Azure AD (credentials + MFA if required)

Step 4: SAML Response

Azure AD generates signed SAML assertion and posts to Salesforce

<samlp:Response>
  <saml:Assertion>
    <saml:Subject>
      <saml:NameID>Nigel@NigelTech.onmicrosoft.com</saml:NameID>
    </saml:Subject>
    <saml:Conditions>
      <saml:AudienceRestriction>
        <saml:Audience>https://orgfarm-ce698c619e-dev-ed...</saml:Audience>
      </saml:AudienceRestriction>
    </saml:Conditions>
    <saml:AttributeStatement>
      <saml:Attribute Name="username">
        <saml:AttributeValue>Nigel@NigelTech.onmicrosoft.com</saml:AttributeValue>
      </saml:Attribute>
    </saml:AttributeStatement>
  </saml:Assertion>
</samlp:Response>

Step 5: Token Validation

Salesforce validates:

  • Digital signature using uploaded certificate
  • Audience restriction matches Entity ID
  • Token not expired (NotOnOrAfter timestamp)
  • NameID matches user's Federation ID

Step 6: Access Granted

Salesforce creates session and grants access
